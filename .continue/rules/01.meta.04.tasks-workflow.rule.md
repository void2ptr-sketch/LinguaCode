# Goal: Keep work aligned with the project task list (`TASKS.md`).

`TASKS.md` is the single source of truth for the MVP checklist and backlog (G-tasks). Always consult it before starting and update it after finishing work.

## Before starting a task

1. Read `TASKS.md` — check the current status of the relevant section (MVP done, backlog G0–G16+).
2. If the task is not listed, add it to the appropriate backlog section as an unchecked item `- [ ] …` before implementing.
3. Check `docs/INDEX.md` for related documentation (domain, architecture, features) and `docs/SYSTEM/GIT-RULES.md` for the branch/commit format.

## During work

- Reference the task ID in the branch name and commit prefix: `NUMBER_description` / `[NUMBER_description] …` (see `01.meta.03.git-workflow.rule.md`).
- Do not silently change scope: if the task grows beyond its checklist item, split it into a new item or note it in `TASKS.md`.

## After completing a task

1. Mark the corresponding item as done: `- [x] …`.
2. If the task introduced new follow-up work, add new unchecked items to the backlog.
3. Update related documentation (`docs/`) when APIs or behavior changed — per project convention, documentation must stay in sync.
4. Run the verification pipeline before finishing: `npm run verify` (lint + audit:fsd + check:imports + audit:barrels + sync:hanzi + build + tests).

## When in doubt

1. Check `TASKS.md` — actual task status.
2. Check `docs/` — domain/architecture documentation.
3. Study existing code in similar features.
4. Do not assume libraries exist without checking `package.json`.
5. Ask a clarifying question only when there is real ambiguity.
