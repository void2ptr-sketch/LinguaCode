# Goal: Keep work aligned with the project task list (`TASKS.md`).

`TASKS.md` is the single source of truth for the MVP checklist and backlog (G-tasks). Always consult it before starting and update it after finishing work.

## Status legend (TASKS.md)

| Marker | Meaning | When to use |
|--------|---------|-------------|
| `[ ]` | Pending — not started | New task, not in progress |
| `[→]` | In progress — agent is working on it | Branch created, changes in flight |
| `[x]` | Done — code written, needs review | Implementation complete, not yet verified |
| `[✓]` | Done + verified — build + tests green | `npm run verify` passed, docs synced |
| `[⊘]` | Cancelled / superseded | Replaced by another task or abandoned |
| `[!]` | Blocked — needs decision or external input | Waiting on backend, design, or user |

- Use `[→]` only when actively implementing; mark `[x]` immediately after coding, `[✓]` only after verification.
- Never mark `[✓]` without running `npm run verify` first.

## Definition of Done (per subtask)

Every subtask (`G11a`, `G14b`, `H15c`…) must pass **all** applicable checks before marking `[✓]`:

| Check | When applies | Command / Action |
|-------|-------------|------------------|
| File exists | Every subtask | Verify path from TASKS.md resolves |
| Barrel export | New `index.ts` | `npm run audit:barrels` |
| FSD layers | `src/app/` changes | `npm run audit:fsd` |
| Import resolution | After moving files | `npm run check:imports` |
| Build | Code changes | `npm run build:prod` |
| Tests | Code changes | `npm run test:ci` |
| Coverage | New features | `npm run test:coverage` (80/80/80/80) |
| Docs synced | API / behavior changes | Update relevant `docs/` file |
| Conformance | API / mock changes | `npx ng test --include='**/*.conformance.spec.ts'` |

**Minimal DoD** (always required): file exists + build + tests + `npm run verify`.

## Same-commit sync (code ↔ documentation)

When a task changes **API, behavior, or architecture** — documentation must be updated **in the same commit**:

1. Implement code changes
2. Update the relevant `docs/` file (e.g., `ARCHITECTURE.<slice>.md`, `DOMAIN.md`, `FEATURES/*.md`)
3. Mark TASKS.md item as `[✓]` (only after `npm run verify`)
4. Commit together: `[NUMBER_desc] implement X + update docs/Y.md`

**Rule:** never commit code changes that affect public API or behavior without updating docs. If docs are out of sync, fix them in the same task — do not create a separate "docs only" commit.

## Before starting a task

1. Read `TASKS.md` — check the current status of the relevant section (MVP done, backlog G0–G17+).
2. If the task is not listed, add it to the appropriate backlog section as an unchecked item `- [ ] …` before implementing.
3. Check `docs/INDEX.md` for related documentation (domain, architecture, features) and `docs/PROCESS/GIT-RULES.md` for the branch/commit format.
4. Identify which `docs/` file(s) must be updated (see "Same-commit sync" above).

## During work

- Reference the task ID in the branch name and commit prefix: `NUMBER_description` / `[NUMBER_description] …` (see `01.meta.03.git-workflow.rule.md`).
- Do not silently change scope: if the task grows beyond its checklist item, split it into a new item or note it in `TASKS.md`.
- Update TASKS.md status to `[→]` when starting, `[x]` after coding, `[✓]` after verification.

## After completing a task

1. Mark the corresponding item as `[✓]` in `TASKS.md` (only after `npm run verify` passes).
2. If the task introduced new follow-up work, add new unchecked items to the backlog.
3. Run the verification pipeline: `npm run verify` (lint + audit:fsd + check:imports + audit:barrels + sync:hanzi + build + tests).
4. Verify DoD checklist — all applicable checks must pass.
5. Update related documentation (`docs/`) if API or behavior changed — per "Same-commit sync" rule.

## When in doubt

1. Check `TASKS.md` — actual task status.
2. Check `docs/` — domain/architecture documentation.
3. Study existing code in similar features.
4. Do not assume libraries exist without checking `package.json`.
5. Ask a clarifying question only when there is real ambiguity.
