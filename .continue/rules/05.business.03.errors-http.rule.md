# Goal: Follow the project's error handling and HTTP infrastructure patterns.

## HTTP client setup

- HTTP is configured once in `src/app/app/api/provide-api.http.ts` via `provideApiHttp()`:
  `provideHttpClient(withFetch(), withInterceptors([...]))`.
- The interceptor pipeline (order matters): mock interceptors (conditional on environment flags) → `offlineInterceptor` → `authRefreshInterceptor` → `authInterceptor` → `retryInterceptor` → `timeoutInterceptor` → `errorInterceptor`.
- **Do not create ad-hoc `HttpClient` providers** in components/features — use the shared `provideApiHttp()` from `app.config.ts`.
- Mock interceptors are enabled via environment flags (`useCardsApiMock`, `useScenariosApiMock`, `useCoursesApiMock`) — see `docs/SYSTEM/MOCK-DATA.md`.

## Error handling

- **Every HTTP pipeline must handle errors** — use `catchError` to transform errors into manageable state (error signal, user-friendly message, or rethrow for global handling). Never leave HTTP observables without explicit error handling (see `03.angular.03.reactive.rule.md`).
- **Global error handler**: `AppErrorHandler` (`src/app/app/errors/app-error-handler.ts`) catches unhandled errors, logs via `AppLoggerService`, and surfaces a user-facing toast via `ErrorToastService`. Do not bypass it; keep it minimal.
- **Logging**: use `AppLoggerService` (`src/app/shared/logger/`) for logging — do not use `console.log` directly in services/components.
- **User-facing errors**: use `ErrorToastService` (`src/app/shared/ui/error-toast/`) for toasts; do not invent new toast mechanisms.

## Offline mutations (sync queue)

- Offline mutations are queued via `SyncQueueService` (`src/app/shared/sync/`) and replayed when the network returns.
- Executors are registered in `SyncQueueBootstrap` (`src/app/app/sync/sync-queue.bootstrap.ts`) for `card.*`, `scenario.*`, `course.*` operations; the queue is flushed on app startup.
- When adding a new mutable entity, register its executor in `SyncQueueBootstrap` and use the queue for offline-capable writes instead of direct API calls.

## Rules

- Do not swallow errors silently — always log and/or surface them.
- Do not add new global providers for HTTP/errors — extend the existing pipeline in `provide-api.http.ts` / `app.config.ts`.
- Keep error messages user-friendly and localized to the domain language (Russian/English).
