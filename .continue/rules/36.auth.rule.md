# Goal: Keep authentication flows consistent — store, tokens, interceptors, guards.

## Auth state

- `AuthStore` (`entities/auth/services/auth.store.ts`) is the **single auth state**: user, token lifecycle, session restore.
- Session restore runs at startup via `provideAppInitializer` in `app.config.ts` (see `CONTINUE.md` §3).

## Tokens

- Tokens are stored/read through `AuthTokenStorage` — **never** write tokens to `localStorage` directly and never inline them in components.
- HTTP auth is applied by `authInterceptor` (`Authorization: Bearer <accessToken>`) and refresh by `authRefreshInterceptor`; pipeline order is fixed in `provideApiHttp()` (see `20.errors-http.rule.md`) — do not add ad-hoc auth logic to services.
- `authEnabled` environment flag controls real vs. mock auth flow (see `24.env-api-contract.rule.md`). When `false`, the mock flow must not require a real backend.

## Guards

- Use functional guards (`canMatch` / `canActivate`) — no class-based guards (see `21.routing.rule.md`).
- `canMatch` for availability (feature access), `canActivate` for access control on a matched route.
- Guards read `AuthStore` state; feature-scoped guard providers go in the route `providers` array (see `04.angular.DI-PS.rule.md`).

## Rules

- Do not bypass `authInterceptor` with a second `HttpClient` provider; extend the shared pipeline instead.
- Log auth failures via `AppLoggerService`; surface user-friendly errors (see `20.errors-http.rule.md`, `34.i18n.rule.md`).
- Never commit tokens or secrets (see `10.angular.security.rule.md`).
