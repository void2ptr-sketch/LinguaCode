# Goal: Keep client-side storage consistent — IndexedDB for data, localStorage for small prefs, abstraction via persistence services.

## Layers

- **IndexedDB** — the durable store for app data:
  - `IndexedDbService` (`shared/storage/`) is the single wrapper; no direct `indexedDB` calls elsewhere.
  - Used by: `ContentSeedRepository` (cached seed snapshots), `SyncQueueService` (offline mutations, see `20.errors-http.rule.md`).
- **localStorage** — only small preferences and the user-content overlay:
  - Overlay key `lingua-code.user-content.v1` (`USER_CONTENT_OVERLAY_KEY`) — **never change the key or version without a migration path** (see `18.data-content.rule.md`).
  - Preferences persisted via `UserPersistence`, learning results via `LearningResultsPersistence` — **do not** read/write `localStorage` directly in components.

## Persistence services

- Persistence is abstracted behind `*.persistence.ts` services that (de)serialize and validate the shape — components interact with stores, never with storage APIs.
- Schema changes require versioned migration logic; do not silently drop old fields (see `18.data-content.rule.md` critical fields).

## Security

- Do not store tokens or secrets in `localStorage` (see `10.angular.security.rule.md`, `36.auth.rule.md`).
- Content cached in IndexedDB / service worker must not include sensitive user data (see `22.pwa.rule.md`).

## Rules

- New persistent data → add an `IndexedDbService`-based repository/persistence service; keep naming `*.persistence.ts` / repositories.
- Handle storage errors (quota, unavailability): log via `AppLoggerService`, surface a friendly error, degrade gracefully.
- Mock storage in tests (the codebase uses fake IDB implementations in specs — follow that pattern).
