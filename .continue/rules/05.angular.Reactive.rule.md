# Goal: Keep RxJS usage clean, composable, and testable.

## RxJS Guidelines

- **Use higher‑order operators only when necessary.**  
  `switchMap` is the default choice for typical user‑triggered requests (e.g., search input, button clicks) because it cancels previous pending subscriptions and avoids overlapping responses.  
  However, `switchMap` is not universally required:
  - Use `mergeMap` when you intentionally need to keep multiple concurrent requests active (e.g., parallel data fetches that must all complete).
  - Use `concatMap` when order and sequential execution matter (e.g., batch operations where each request must finish before the next starts).
  - Use `exhaustMap` when you want to ignore new user actions while a current request is in progress (e.g., preventing duplicate form submissions).

- **Always handle errors with `catchError` in HTTP calls; avoid silent failures.**  
  Every observable pipeline that performs remote calls should end with a `catchError` operator to transform errors into a manageable state (e.g., set an error signal, emit a user‑friendly message, or rethrow for global error handling). Never leave HTTP-related observables without explicit error handling.

- **Do not return raw observables from template methods; expose them as properties or use `async` pipe in templates.**  
  Template expressions should not invoke functions that return observables on every change detection cycle. Instead:
  - Expose the observable as a class property.
  - In the template, use the `async` pipe to subscribe and unsubscribe automatically.
  This pattern prevents memory leaks and ensures consistent subscription lifecycle management.

- **Avoid nested subscriptions; prefer flattening with operators.**  
  Nested `.subscribe()` calls are a code smell that leads to unmanaged subscriptions, potential memory leaks, and complex error propagation. Use operators like `switchMap`, `mergeMap`, `concatMap`, or `flatMap` to flatten inner observables into a single stream. If multiple sources must be combined, prefer `combineLatest`, `forkJoin`, or `zip` over manual nested subscriptions.

- **For side effects, consider `effect` (Angular 16+) instead of `tap` with side effects in streams.**  
  When the primary goal of a side effect is to react to value changes (e.g., updating UI state, logging, triggering animations), prefer Angular’s `effect` over `tap`.  
  - `effect` is designed for reactive side effects tied to the change detection cycle and integrates cleanly with Signals.
  - Reserve `tap` for debugging, logging, or minor inline actions within the stream itself, not for core business logic side effects.

## When to Use Signals vs. RxJS Streams

Choose based on the nature of the data and its consumption pattern:

### Prefer Signals when:
- The data represents **local component state** (e.g., form inputs, toggle flags, loading indicators, selected items).
- You need **fine‑grained reactivity** with minimal overhead and automatic change detection updates.
- The value is consumed directly in the template via interpolation or signal expressions.
- You want to compose state using `computed` and `effect` for clear, synchronous derivation and side effects.
- The source is **synchronous or derived locally** without complex time‑based transformations.

Signals provide a simpler mental model for most UI state and reduce the risk of memory leaks and subscription mismanagement.

### Prefer RxJS Streams when:
- You are dealing with **asynchronous event sources** that require time‑based operators (e.g., debouncing, throttling, buffering, windowing).
- You need to compose multiple asynchronous sources with sophisticated merging, switching, or error recovery strategies.
- The observable represents an **external event stream** (e.g., WebSocket messages, router events, user input streams with debounce).
- You must handle **retries, timeouts, and complex backpressure** scenarios.
- Integration with libraries or APIs that expose observables as their primary interface.

In practice, a modern Angular codebase often uses **Signals for local state** and **RxJS for event streams and external data flows**, combining them via `toSignal`/`toObservable` only when interoperability is strictly required.
